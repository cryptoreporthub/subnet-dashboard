## The verdict: the live weight nudge is driven by the **string-based `_normalize_expert`** — NOT signal attribution

This is confirmed by the literal code in `internal/council/resolver.py` (`_stamp_and_nudge_expert`):

```python
def _stamp_and_nudge_expert(prediction, *, correct):
    """Stamp rich attribution on the row; nudge only pre-stamp normalize (Grok LOCK)."""
    nudge_expert = _normalize_expert(prediction)                # <- drives the WEIGHT
    stamped_expert, expert_source = resolve_expert_attribution(prediction)  # <- drives the LABEL only
    if stamped_expert:
        prediction["expert"] = stamped_expert
        ...
    if nudge_expert and not _skip_council_learning(prediction):
        _nudge_weights(bool(correct), nudge_expert)             # <- uses _normalize_expert
```

Two different experts are computed from the **same prediction row**, and they're allowed to disagree:
- **`_normalize_expert`** → `normalize_expert()` in `expert_attribution.py`: substring match on the raw `expert` / `signal_source` **string**. `alpha→quant`, `beta→hype`, `gamma→dark_horse`, and the substring rules (`"quant"/"fundamental"/"yield"→quant`, etc.).
- **`resolve_expert_attribution`** → the full signal/replay/pick-blend pipeline. But look at the docstring: it says *"attribution — normalize, stamp, and measure (not weight nudge)."* It's only used to **re-stamp `prediction["expert"]` on the ledger row**. It **never** feeds `_nudge_weights`.

So on every live resolution:
1. Row is graded (correct/wrong).
2. `_normalize_expert` reads the **raw, creation-time** `expert`/`signal_source` string (it runs *before* any re-stamp, and the docstring literally calls this the "Grok LOCK" behavior).
3. Whatever that crude substring matcher returns is the expert whose weight gets nudged.
4. The fair, signal-based attribution only fixes the row's label afterward — cosmetic.
